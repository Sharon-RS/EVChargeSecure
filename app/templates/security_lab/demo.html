Secure Software Engineering Vulnerability Showcase

This interactive laboratory module demonstrates the 6 critical vulnerabilities identified during threat modeling, contrasted directly against their implemented secure production defenses. Use the controls below to observe exploit mechanics vs zero-trust enforcement in real time.

1. SQL Injection (CWE-89)

Threat: Station search query manipulation allowing authentication or schema bypass
⚠️ Critical Severity
❌ Vulnerable Implementation
# Dynamic string formatting enables SQL syntax injection
raw_sql = f"SELECT * FROM stations WHERE name LIKE '%{user_query}%'"
results = cursor.execute(raw_sql).fetchall()
✓ Secure Parameterized Fix
# Parameterized query engine isolates data from instructions
safe_sql = "SELECT * FROM stations WHERE name LIKE ?"
results = cursor.execute(safe_sql, (f"%{user_query}%",)).fetchall()

2. Plaintext Password Storage (CWE-256 / CWE-312)

Threat: Storing credentials in clear text compromises all accounts upon DB breach
⚠️ Critical Severity
❌ Vulnerable Implementation
# Storing unencrypted string directly in database
cursor.execute("INSERT INTO users (username, password) VALUES (?, ?)", 
               (username, raw_password))
✓ Secure Password Hashing
# Werkzeug Scrypt/PBKDF2 with CSPRNG salt & high work factor
password_hash = generate_password_hash(raw_password)
cursor.execute("INSERT INTO users (username, password_hash) VALUES (?, ?)", 
               (username, password_hash))

3. Broken Authorization & Missing RBAC (CWE-285)

Threat: Unprivileged user invokes administrative function to alter hardware power ratings
⚠️ High Severity
❌ Vulnerable Implementation
# Endpoint only checks if user is logged in, but neglects role
@app.route("/admin/tune-power", methods=["POST"])
@login_required
def update_power():
    apply_power_limits(...) # Any logged-in user can execute!
✓ Secure RBAC Decorator
# @admin_required enforces session.get('role') == 'ADMIN'
@app.route("/admin/tune-power", methods=["POST"])
@admin_required
def update_power():
    apply_power_limits(...) # Strictly restricted to ADMIN role

5. Concurrent Slot Reservation Race Condition (CWE-362)

Threat: TOCTOU race allows 2 drivers to book the same charger simultaneously
⚠️ High Severity
❌ Vulnerable Implementation (TOCTOU)
# Check and update separated: concurrency window opens
point = db.execute("SELECT status FROM points WHERE id = ?", (id,)).fetchone()
if point["status"] == "AVAILABLE":
    # Time gap occurs here during high load
    db.execute("UPDATE points SET status = 'RESERVED' WHERE id = ?", (id,))
✓ Atomic Test-and-Set Lock
# Atomic single-statement update guarantees isolation
cursor.execute("UPDATE points SET status = 'RESERVED' WHERE id = ? AND status = 'AVAILABLE'", (id,))
if cursor.rowcount == 0:
    raise ConflictError("Point was reserved by concurrent request")

6. Insecure Direct Object Reference / IDOR (CWE-639)

Threat: Manipulating session_id parameter to view other drivers' private sessions/receipts
⚠️ High Severity
❌ Vulnerable Implementation
# Object retrieved strictly by ID without asserting ownership
@app.route("/receipt/")
def get_receipt(id):
    return db.execute("SELECT * FROM payments WHERE id = ?", (id,)).fetchone()
✓ Horizontal Scoping (Owner Binding)
# Record must match both object ID AND the caller's session user_id
@app.route("/receipt/")
@login_required
def get_receipt(id):
    return db.execute("SELECT * FROM payments WHERE id = ? AND user_id = ?", 
                      (id, session['user_id'])).fetchone()
